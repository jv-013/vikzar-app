### Fixed — Phase 2 Freeze Review

A staff-level audit of every specification document against a 10-point checklist found one BLOCKER, five WARN, and two RECOMMEND findings (full audit delivered separately, not persisted as a file). All approved findings were corrected in this pass; `ROADMAP.md` Phase 2 moved **Pending Freeze → Frozen**.

- **Onboarding rewritten to the frozen six-screen flow** (BLOCKER): `DESIGN_SPECIFICATION.md` §19.1, §17.1, and §16 rewritten. The prior flow had grown to 9–12 effective screens (a separate Welcome screen, multi-step Authentication, a split Profile Setup/Football Profile, four separate full-screen Permissions steps, and an unrequested "Welcome confirmation" screen) — none of which matched the "maximum 6–7 screens" constraint from Phase 2A or Product Principle 5. Now: Splash → Workspace Selection → Level → single Profile Form (with inline-expandable injury history) → single consolidated Permissions screen → Connect Pod / Create-Join Team → Home. Authentication is retained as a required, single-screen identity gate, explicitly documented as uncounted infrastructure (like Splash), not one of the six. Training Frequency is folded into the single Profile Form rather than dropped. Screen Inventory renumbered accordingly (28 → 26 screens).
- **"Home" naming standardized** (WARN): all "Dashboard"/"Player Dashboard"/"Coach Dashboard" references in `DESIGN_SPECIFICATION.md` (bottom nav destination column, onboarding flow diagram, Coach onboarding wireframe, type-scale example) replaced with "Home" throughout.
- **List Row component added** (RECOMMEND): a new formal component in `DESIGN_SPECIFICATION.md` §18 (anatomy, height, radius/elevation treatment, grouping, states), with Settings, Pod Connection, and Team — Roster tab wireframes updated to reference it explicitly instead of describing ad hoc "simple rows."
- **Alert Crimson approved and scoped** (WARN): `DESIGN_SPECIFICATION.md` §8 now states Alert Crimson is the one sanctioned exception to the five-colour palette, approved at this freeze review, and **scoped exclusively to Critical risk-level indicators** (risk chip/ring, persistent Critical alert banner, Alert Inbox Critical entries). The "Deep Rose" derived colour previously used for High risk is removed; High now uses official Oxide Rose with a stronger visual *weight* (filled chip, bold label, filled icon) instead of a new hue, keeping it within the five-colour palette. Destructive buttons, Text Field error states, and Error Screens — previously using Alert Crimson — now use Oxide Rose, preserving Alert Crimson's rarity as a dedicated safety signal.
- **ADR-031 data model resolved** (RECOMMEND): `DECISIONS.md` ADR-031 updated with the finalized schema — `users/{uid}.workspaces` (a structured object; `workspaces.player.teamId`, `workspaces.coach.teamIds`, each key present only if that workspace is held) and `users/{uid}.defaultWorkspace` (onboarding-time fallback only). **No `activeWorkspace` field in Firestore** — the currently active workspace is local, per-device app state (Riverpod + local storage), never synced to the server, avoiding both a per-switch Firestore write and a multi-device consistency problem. `BACKEND_SPECIFICATION.md` §1.5 (schema, Written-by/Read-by note, example JSON), §2 (relationships), §3 (Authentication Mapping table), §5 (Coach Ownership Model), §22 (read contract), and §23 (future scalability) updated to match; `ARCHITECTURE.md` §9, §10, §19, and §23 updated to reference `workspaces` instead of the retired `role` field. The `teams/{teamId}/members/{uid}.role` roster field (a distinct, per-team concept — "player" vs. a future "assistant_coach" roster role) was correctly left untouched throughout.
- **Recovery/Readiness metrics not added, by design** (RECOMMEND, declined): confirmed absent from `DESIGN_SPECIFICATION.md`'s Player dashboard and noted explicitly in its Assumptions — neither concept exists in `BACKEND_SPECIFICATION.md`'s data model, and inventing one would mean originating a new laptop ML/Risk Engine output outside this audit's scope.
- `DESIGN_SPECIFICATION.md`'s Open Questions and Assumptions updated to close the resolved items (onboarding, Alert Crimson, List Row, `users/{uid}` data model) and its Document Control status set to **Frozen**.

### Added — Phase 5: Identity & Access

The first real user experience. This phase implements complete authentication, session persistence, the workspace/role model, and full navigation routing — deliberately stopping at the boundary of onboarding, Player Home, and Coach Home, which remain unbuilt placeholders.

- **Official brand assets imported.** `assets/branding/vikzar_icon.svg` (icon-only mark) and `vikzar_logo_lockup.svg` (two-color full lockup) added verbatim, unmodified, from the supplied brand asset kit. `VikzarIcon` (`design_system/components/vikzar_icon.dart`) renders the icon mark via `flutter_svg`, tinted at runtime with `ColorFilter.mode(color, BlendMode.srcIn)` rather than by editing the asset — the only way to place a dark-ink mark correctly on Vikzar's Plum-Black-first UI. The two-color lockup is registered but deliberately **not placed on any dark screen**: it is a two-color design that destructive single-color tinting would erase, and no light-background placement exists yet in the shipped screens; documented as an intentional, explained gap rather than silently unused. `SplashScreen` now renders `VikzarIcon` in place of the Phase 4 placeholder wordmark text.
- **Permanent Design Principle added** to `DESIGN_SPECIFICATION.md` §3, verbatim, as the interpretive lens for every future design decision: the interface should "appear carved from darkness," colour exists only to communicate meaning, motion communicates continuity rather than excitement, and depth comes from spacing/blur/elevation rather than decoration.
- **Colour philosophy frozen and swapped**, recorded as [`DECISIONS.md` ADR-039](DECISIONS.md#adr-039-colour-philosophy-freeze--oxide-rose-as-primary-action-mineral-blue-as-secondary-informational-accent): Oxide Rose becomes the primary action/interactive colour (buttons, focus rings, primary CTAs); Mineral Blue moves to secondary/informational accent (charts, status detail) — the inverse of the Phase 2A/4 assumption. `DESIGN_SPECIFICATION.md` §8's colour tables, Usage Ratios, and every §18 component cross-reference (Buttons, Text Fields, Segment Controls, Bottom Nav, Loading Indicator, focus ring) updated to match; `AppTheme.light()`/`.dark()` updated (`ColorScheme.primary` = Oxide Rose, `.secondary` = Mineral Blue). - **Active workspace as local device state, never Firestore** — `ActiveWorkspaceStore` (`SharedPreferences`-backed) and `activeWorkspaceProvider`/`ActiveWorkspaceNotifier` implement the "no `activeWorkspace` field in Firestore" rule from ADR-031 in code for the first time.
- **Firebase Authentication architecture implemented**, email/password only for MVP, against a **placeholder Firebase configuration** (`PlaceholderFirebaseOptions`, [`DECISIONS.md` ADR-042](DECISIONS.md#adr-042-placeholder-firebase-configuration-for-pre-project-development)) since no real Firebase project exists yet: `AuthDatasource` (interface) / `FirebaseAuthDatasource` (implementation) separates business logic from the `firebase_auth` SDK, enabling full unit testing via a `FakeAuthDatasource` without mocking Firebase. `AuthRepository`/`AuthRepositoryImpl` implements a **single-screen sign-in-or-create-account flow** ([`DECISIONS.md` ADR-040](DECISIONS.md#adr-040-single-screen-sign-in-or-create-account-authentication-flow)): sign-in is attempted first, and account creation is attempted only on a "no such account" failure, correctly distinguishing that case from "wrong password" across the Firebase Auth SDK error-code versions that do and do not still separate the two. Every Firebase-touching call is routed through the existing `Result`/`Failure` architecture ([`DECISIONS.md` ADR-020](DECISIONS.md#adr-020-error-handling--typed-resultfailure-pattern)); `FailureMessageMapper` translates failures into calm, specific user-facing copy, never a raw error code.

Protects all routes beyond Splash/Auth behind authentication, and is structured to support future deep linking.

### Added — Phase 6: Complete Onboarding Experience

The complete Player and Coach onboarding flows, end to end — Workspace Selection through an Onboarding Complete terminal screen. Player Home, Coach Home, live monitoring, analytics, Bluetooth communication, Firestore writes, and Cloud Functions all remain explicitly out of scope, per this phase's own boundary.

- **Authentication rewritten from email/password to passwordless email + 6-digit code**, recorded as [`DECISIONS.md` ADR-043](DECISIONS.md#adr-043-passwordless-email-otp-authentication-replaces-email--password) (supersedes Phase 5's [ADR-040](DECISIONS.md#adr-040-single-screen-sign-in-or-create-account-authentication-flow)): there is no password, confirm-password, forgot-password, or password-complexity concept anywhere in the product. `AuthDatasource`/`AuthRepository` gained `sendOtp`/`verifyOtp`, replacing `signIn`/`signInOrCreateAccount`'s password-facing surface. `AuthScreen` is now a two-step flow (email, then code) with a restrained slide-with-fade transition between steps, a 30-second resend cooldown, and a new `VikzarOtpField` component (6 individually-boxed digits, auto-advancing focus, backspace-to-previous, and paste/autofill distribution across boxes).
- **Placeholder OTP verification**, recorded as [`DECISIONS.md` ADR-044](DECISIONS.md#adr-044-placeholder-otp-verification-pending-real-backend-delivery): with no Cloud Functions or email delivery this phase, `AuthRepositoryImpl.verifyOtp` accepts any syntactically valid 6-digit code, internally signing in (or transparently creating an account) against Firebase Auth's real email/password mechanism via a secret deterministically derived from the email (SHA-256, never shown to or typed by the user, never exposed by any public method). This preserves real Firebase session/UID/persistence semantics today and is explicitly flagged, in both the ADR and the code, as **not safe for production** until replaced by real server-issued/verified codes.
- **Typography frozen**, recorded as [`DECISIONS.md` ADR-045](DECISIONS.md#adr-045-typography-freeze--nohemi-headings--inter-body): Nohemi for the four heading-weight type-scale steps, Inter for the four body/UI steps. Inter is implemented via the newly-added `google_fonts` package, resolving the Phase 4 Open Question. Nohemi's font asset is not sourced this phase (a licensed commercial typeface — not something a phase brief can provision on its own); headings render with the platform default system font at a single documented swap point in `vikzar_text_theme.dart`, an intentionally visible placeholder rather than a silent Inter substitution.
- **Onboarding routing defect found and fixed**, recorded as [`DECISIONS.md` ADR-046](DECISIONS.md#adr-046-onboarding-is-router-gated-as-a-subtree-with-local-per-workspace-completion-tracking): Phase 5's `routeDestinationProvider` checked Firestore's `workspaces` field (always empty — no Cloud Function ever populates it, per ADR-041) *before* consulting the local active-workspace pointer, and forced an exact-path redirect on every recomputation. This meant Workspace Selection could never actually navigate forward — a user selecting a workspace was silently bounced back to Workspace Selection forever. Never surfaced in Phase 5 because that phase's scope stopped at a single placeholder screen reachable directly from Workspace Selection. Fixed by gating an entire onboarding **subtree** (`/onboarding/{workspace}/**`) rather than one exact path, and adding `OnboardingProgressStore`/`onboardingCompletionProvider` (a local, per-workspace "has this device completed onboarding" record, mirroring `ActiveWorkspaceStore`'s pattern) so a returning user lands on Onboarding Complete rather than repeating every step on each cold start.
- **Player onboarding built in full**: Playing Level (Academy / Amateur / Semi Professional / Professional), a single Profile Form (Name, Age, Height, Weight, Preferred Foot, Playing Position) with Injury History (Never / Previously / Currently Recovering) expanding inline to ACL/Meniscus/Hamstring/Ankle/Other chips on "Previously" — never a new screen, Permissions (Bluetooth/Motion/Notifications, UI-only toggles this phase — not wired to live OS prompts, native platform configuration being out of a UI-focused phase's scope), a Connect Pod placeholder screen (always "not yet assigned," honest about the laptop-centric MVP model, no Bluetooth implemented), and Onboarding Complete.
- **Coach onboarding built in full**, mirroring the Player flow's shape: Coaching Level (Academy / Club / Professional), Profile (Name, Age, Coaching Title/Role, optional Club/Organization), Permissions (shared `OnboardingPermissionsContent` with Player), Create/Join Team (two selectable cards, each opening an inline field — UI only, no Cloud Function call, nothing persisted), and Onboarding Complete (shared screen, workspace-aware copy).
- **DESIGN_SPECIFICATION.md and ARCHITECTURE.md reconciled** against the Phase 6 brief's content changes, each documented as an explicit revision rather than silently diverging from the frozen spec: the auth-gate description (password → OTP), Level option labels (the original draft's Grassroots/Semi-Pro wording → Academy/Amateur/Semi Professional/Professional for Player, Academy/Club/Professional for Coach), Injury History's third "Currently Recovering" state, Training Frequency removed from the Player Profile Form (absent from this phase's explicit field list), Permissions trimmed from four rows to three (Health removed, not in scope), and both onboarding paths now terminating at Onboarding Complete rather than "directly on Home" (Player/Coach Home don't exist yet). New Motion Principle (forward-navigation slide-with-fade, sheet transitions, soft scale-in) added to `DESIGN_SPECIFICATION.md` §12.
- Nine new shared design-system components: `VikzarOtpField`, `VikzarSegmentedControl<T>`, `VikzarChipGroup<T>`, `VikzarExpandableSection`, `VikzarListRow`, plus onboarding-scoped `OnboardingStepScaffold` and `OnboardingPermissionsContent`. Country/language pickers, dialogs, and a generic bottom-sheet component were **not** built — nothing in this phase's actual screen flow calls for them (the Nike reference screenshots were for interaction-quality inspiration only, not a literal screen list), and building unused components would be speculative scope.
- **Testing**: `flutter analyze` — 0 issues. `flutter test` — 61/61 passing, including full rewrites of the auth repository/screen tests for the OTP contract, a rewritten `route_destination_test.dart` covering the subtree-gating fix (with a test specifically proving the Phase 5 regression is resolved), new tests for `VikzarOtpField` (paste/autofill distribution across boxes), `OnboardingProgressStore`, both onboarding flows' domain-model completion logic, and widget tests for the Level, Profile (injury-history expand/collapse), and Create/Join Team screens.
- **Manual verification**: exercised the full passwordless flow in-browser against a `flutter build web` static bundle — email entry, 6-digit code entry with auto-advance across all six boxes and auto-submit on completion, and a graceful calm failure against the placeholder Firebase project, matching the code path `verifyOtp` takes with no real backend. (Extensive, ultimately resolved friction calibrating the browser-automation tool's click coordinates against this Flutter web canvas app's actual CSS-pixel layout — not a product defect; noted here only because it consumed real verification time.)
- Updated `README.md` and `ROADMAP.md` to reflect the completed onboarding flows.

### Added — Phase 7: Player Home, Coach Home & Application Shell

The first complete Vikzar application experience after onboarding — a real, navigable app shell replacing the Onboarding Complete dead end. No Bluetooth, ETL, ML, Live Monitoring, Firestore writes, Cloud Functions, or analytics — every data-dependent section is an honest placeholder, never a fabricated number.

- **Onboarding now hands off to a real Home**, not a terminal screen: revised `routeDestinationProvider` (`routing/route_guards.dart`) with a new `InApp(workspace)` destination — once a workspace's onboarding is locally complete, the router gates the entire app-shell subtree (`/{workspace}/**`) instead of parking the user on "You're all set." forever. `OnboardingCompleteScreen` gained a "Get Started" button (marking completion is now an explicit tap, never automatic on mount, per this phase's "the interaction must be obvious" principle) that hands off directly.
- **A single parameterized application shell** (`AppShellScaffold(workspace:)`, `routing/shells/`), not a Player/Coach scaffold pair, recorded as [`DECISIONS.md` ADR-048](DECISIONS.md#adr-048-a-single-parameterized-app-shell-not-a-playercoach-scaffold-pair): one `StatefulShellRoute.indexedStack` per workspace (Player: Home/Timeline/History/Profile; Coach: Home/Live/Team/Alerts/Profile, per `DESIGN_SPECIFICATION.md` §13's frozen nav-item tables), preserving each tab's state across switches. `AppTheme` gained a `NavigationBarThemeData` (Oxide Rose active / Warm Ivory 64% inactive) so both instances stay visually consistent from one theme definition.
- **Player Home built in full**: Greeting, Connected Pod placeholder, Battery placeholder, Today's Status, Recent Sessions (empty state), Impact Summary/Risk Summary placeholder tiles, Quick Actions, Recent Activity (empty state) — every data-dependent section shows an honest em-dash or empty-state message, never an invented risk score or session.
- **Coach Home built in full, deliberately a different rhythm from Player Home**: Team Status Summary (Normal/Elevated/High — the Elevated/High counts double as the "Elevated Players"/"Critical Players" placeholders named in this phase's brief), Roster preview, Today's Sessions, Recent Alerts, and a Team Actions row (Invite Player/Create Team/Join Team) — team-level, not a personal instrument panel.
- **The profile badge replaces the standalone workspace-switcher pill**, consolidating every account-level action into one entry point, recorded as [`DECISIONS.md` ADR-047](DECISIONS.md#adr-047-the-profile-badge-is-the-single-entry-point-for-account-level-actions). **The single most important behavior this phase adds**: a single-workspace account (every new account, always — Coach access is never automatic) sees the badge as a plain "PLAYER" or "COACH" label with **no chevron, no dropdown, no hint that a second workspace exists**; only an account holding both workspaces sees "PLAYER ▾"/"COACH ▾" and a "Switch Workspace" row. Held workspaces are read from the local `onboardingCompletionProvider` (Firestore's `workspaces` field is never populated without Cloud Functions, per ADR-041/046 — same reasoning applied here). Switching is instant, local-only, no logout, no loading screen, via a new `VikzarBottomSheet` shared component (Elevation 3, `radius-lg` top corners, per `DESIGN_SPECIFICATION.md` §18).
- **"Become a Coach"**: a request flow reachable only from a Player-only account's profile sheet — Coaching Level, Club/Academy Name, Current Role, optional Organization Email, ending at a submitted-for-review confirmation. Recorded as [`DECISIONS.md` ADR-049](DECISIONS.md#adr-049-become-a-coach-is-a-placeholder-request-flow-with-no-real-approval): **no backend exists to act on this request** — an account cannot reach dual-workspace status through it in this codebase today; that state is reachable only via test/provider overrides, exactly as flagged in the deliverables below.
- **Settings, Profile, and Notification Center built**: Settings (grouped rows — Account now shows Email only, no Password row, correctly reflecting Phase 6's passwordless model; Workspace, Notifications, Bluetooth placeholder, Connected Pod placeholder, Privacy/Help/About/Legal, Sign Out, Delete Account). Profile (avatar + name, an "About You" section editable via a new `EditProfileSheet` — edits the same in-memory onboarding-controller state Home already reads, since no Firestore profile write exists yet — Workspace Information, Connected Device Summary, and a real Application Version read via the newly-added `package_info_plus` package rather than a hand-maintained string that could drift from `pubspec.yaml`). Notification Center (`AsyncNotifier`-backed, realistic seeded placeholder notifications, genuine Empty/Loading/Populated states, mark-as-read/mark-all-as-read).
- **Sign Out implemented for the first time** (Settings and the profile sheet) — delegates to the existing `AuthRepository.signOut()`. **Flagged, not fixed**: the local per-device state this app relies on throughout (`activeWorkspaceProvider`, `onboardingCompletionProvider`) is not scoped to a signing-in account, so a second account signing in on the same device after a sign-out would incorrectly inherit the first account's local workspace/completion state. This is a pre-existing architectural assumption (single-account-per-device, implicit since Phase 5/6) that Sign Out's introduction this phase makes newly reachable, not a regression this phase introduced — recorded here as a blocker for Phase 8, not silently left for someone else to rediscover.
- Four new shared design-system components: `VikzarBottomSheet`, plus onboarding-adjacent `SectionEmptyState` (Home's empty-state pattern, shared by both workspaces) — deliberately **not** built: a country/language picker, a generic dialog wrapper, or additional bottom-sheet variants, since nothing in this phase's actual screen flow calls for them.
- **Testing**: `flutter analyze` — 0 issues. `flutter test` — 75/75 passing: rewritten routing tests covering the `InApp` gate, new tests for `ProfileBadge`'s chevron logic (the single-vs-dual-workspace behavior this phase calls out as its most important requirement), `ProfileSheet`'s account-shape-dependent content, `WorkspaceSwitchSheet`, the Become-a-Coach flow, the Notification Center's three states, `AppShellScaffold`'s per-workspace nav-item sets, and both Home screens.
- **Manual verification**: confirmed correct rendering of the Auth screen (unchanged from Phase 6) at both desktop and mobile viewport sizes via a `flutter build web` static bundle. Manual click-through past the Auth screen was not completed this phase — browser-automation click coordinates against this canvas-rendered app proved unreliable in this session in a way not resolved despite substantial effort (documented honestly rather than silently skipped); Home/Shell/Profile/Settings/Notifications/Become-a-Coach behavior is verified instead via the 75-test automated suite (which exercises the exact same taps reliably through Flutter's own test framework, unaffected by browser-coordinate translation) and via the unchanged-since-Phase-6 Auth mechanism's prior confirmed manual verification.
- Updated `README.md` and `ROADMAP.md` to reflect the application shell. Updated `FLUTTER_ARCHITECTURE.md` §4 with the real, as-built route table (replacing the original aspirational sketch) and `DESIGN_SPECIFICATION.md` §13/§16/§19.2/§19.3 with the profile-badge consolidation, updated Settings/Home wireframes, and the new Profile Sheet/Switch Workspace/Become a Coach screen inventory rows.

Infrastructure only — no UI, navigation, onboarding, Home screens, Firestore business logic, Cloud Functions, or production authentication were touched. The objective was to prepare this codebase for a real Firebase project and correct product-description wording that incorrectly framed Vikzar as a medical/injury-prevention product.

- **Terminology corrected repository-wide**: every instance of "football injury prevention" / "injury intelligence platform" (`SPECIFICATION.md`, `DESIGN_SPECIFICATION.md`, `README.md`, `pubspec.yaml`, `web/manifest.json`, `web/index.html`) replaced with "sports performance and biomechanics analytics platform," matching the explicit product-direction terminology (impact monitoring, biomechanics, movement analysis, elevated injury risk, player insights, training intelligence, performance analytics).
