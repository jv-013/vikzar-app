# Vikzar Security Threat Model

**Status:** Phase 13 — Production Hardening, Dual Workspace Architecture & Security Audit.
**Scope:** every realistic attack scenario named in the Phase 13 brief's Section 6/7, checked directly against this repository's `firestore.rules`, `functions/src/`, and Flutter client code — not a generic checklist. Each row states what's already mitigated (with the exact rule/check cited) versus what was a real, confirmed gap this pass fixed.

## Method

Firestore Security Rules are the mandatory, server-enforced access-control layer (`BACKEND_SPECIFICATION.md` §0/§15) — client-side restriction is UX only, never relied on for safety here. Every Cloud Function additionally treats `request.data` as adversarial input (§8) and derives authorization from the caller's verified identity (`request.auth.uid`/`request.auth.token`) cross-checked against Firestore, never from a value the caller merely claims.

## Scenario-by-scenario

| Scenario | Verdict | Mechanism |
|---|---|---|
| Player modifies another user's `users/{uid}` document | **Mitigated** | `firestore.rules` `users/{uid}` `update`: `isSelf(uid)` gate — `request.auth.uid` must equal the path's `uid`. |
| Forged role values (self-granting `workspaces.coach`) | **Mitigated** | The `workspaces`/`defaultWorkspace` fields are in the client's write allowlist (self-service onboarding, ADR-051), but **granting a workspace via Become-a-Coach approval is Cloud-Function-only** (`approveCoachRequest`, admin-claim-gated, `functions/src/callable/approveCoachRequest.ts`) — a client can complete their *own chosen* workspace at signup, never grant themselves a *second* one through approval. |
| Replay requests (re-submitting an old laptop payload) | **Mitigated** | `ingestLiveTick` rejects any `sequenceNumber` ≤ the currently-stored value as an idempotent no-op (`ingestLiveTick.ts`) — a replayed tick can't move state backward or duplicate a write. |
| Modified/malformed payloads to Cloud Functions | **Mitigated (this pass)** | Every `parse*Payload` in `contracts/types.ts` now calls `requireExactShape` (rejects unknown top-level fields) and range/length-bounds every numeric/string field with a documented range (Phase 13 §8) — previously fields were type-checked but not bounded, and extra fields were silently accepted. |
| Forged `sessionId` (guessing/reusing another team's session) | **Mitigated (this pass)** | `ingestLiveTick`/`submitAlert`/`submitReport` now derive `teamId` from the *stored* `sessions/{sessionId}` document, not the caller's claimed `teamId` — previously the claimed value was trusted directly (a confirmed real gap, fixed). `startSession` itself still requires a fresh, non-colliding `sessionId` (`already-exists` rejection). |
| Forged `teamId` (claiming to belong to a team the caller doesn't) | **Mitigated** | `requireTeamInScope` checks the ingestion principal's `teamIds` claim (laptop side); `requireCoachOfTeam` (`lib/coachAuth.ts`) checks `teams/{teamId}.coachIds` in Firestore for the Coach-callable path (`createPlannedSession`) — never the caller's own claim. |
| Forged `reportId`/report content | **Mitigated** | `reports/{reportId}`: `allow write: if false` — Cloud-Function-only (`submitReport`, `weeklySummaryAggregator`), never client-writable in any form. |
| Client manually writes documents (bypassing the app's own UI, using the Firestore SDK/console directly) | **Mitigated** | Rules are the enforcement boundary, not the app's UI — every safety-relevant collection (`sessions`, `alerts`, `reports`, `plannedSessions`, `devices` telemetry fields) denies client writes regardless of which code path attempts them. |
| Client directly creates `alerts` | **Mitigated** | `alerts/{alertId}`: `allow create: if false` — Cloud-Function-only (`submitAlert`, `deviceHeartbeatMonitor`). The only client write permitted is `acknowledged`/`acknowledgedBy`/`acknowledgedAt` on an *existing* alert, and (this pass) `acknowledgedBy` must equal the caller's own uid. |
| Client calls Cloud Functions manually (not through the app UI) | **Partially mitigated, documented gap** | Every Callable independently authorizes and validates its own payload regardless of caller — calling one directly with a valid ID token is no different from calling it through the UI, by design (this is *supposed* to work, e.g. for the laptop pipeline). What's not yet enforced: **App Check** (Phase 13 §9) would additionally require the call originate from a registered, attested Vikzar client build — wired client-side (`lib/services/firebase/app_check_service.dart`) and documented (`functions/src/lib/appCheck.ts`) but **not yet enforced** on any function, since flipping it on before every real client sends tokens would break existing installs. See Remaining Risks. |
| Client manipulates timestamps | **Mitigated** | Every safety-relevant timestamp (`triggeredAt`, `tickTimestamp`, `createdAt`, `updatedAt`, `serverReceivedAt`) on Cloud-Function-written documents is either the server's own `Timestamp.now()` or validated via `requireIsoTimestamp` (type/parseability only — no forward/backward bound exists today, a documented residual gap, see Remaining Risks) — never a raw client value written unchecked. |
| Client changes ACL/risk scores | **Mitigated (this pass, tightened)** | `riskScore`/`confidence`/`dataCompleteness`/`overallRiskScore` are all Cloud-Function-only fields (never client-writable per Security Rules) and now range-bounded (0.0–1.0, matching their documented scale) rather than merely type-checked — an ingestion principal (the only party ever able to write them) can no longer send an out-of-range or nonsensical value that Firestore would have silently stored. |
| Privilege escalation (Player → Coach without going through the real flow) | **Mitigated** | The only path to `workspaces.coach` is (a) choosing Coach at signup for a brand-new account, or (b) `approveCoachRequest`, admin-claim-gated. No client write path can set `workspaces.coach` on an *existing* Player-only account. |
| Role escalation via forged custom claims | **Mitigated** | Custom claims (`ingestor`, `admin`) are Firebase Auth server-side state, settable only via the Admin SDK (`setCustomUserClaims`) — a client can never set its own claims, regardless of what it sends in a payload. `requireIngestionPrincipal`/`requireAdminPrincipal` read `request.auth.token`, which Firebase itself populates from the verified claim, not from client input. |
| Arbitrary writes (any collection, any field) | **Mitigated** | Every collection audited (12 in the original pass + `plannedSessions`/`_rateLimits` this phase) has an explicit rule; default is deny (`match /{document=**}` has no fallback `allow` anywhere in `firestore.rules`). |
| Arbitrary reads / enumeration / collection-group abuse | **Mitigated** | Every subcollection (`members`, `liveMonitoring`, `notifications`) is gated on auth-derived conditions (`isCoachOfTeam`/`isSelf`), not on filterable document content — Firestore denies an unscoped collection-group query against these rather than silently returning a filtered subset. Confirmed by direct rule audit, not assumption. |
| Abuse through repeated requests (cost/DoS) | **Partially mitigated (this pass)** | `enforceRateLimit` (`lib/rateLimit.ts`) now bounds `ingestLiveTick` (20/sec/principal) and `createPlannedSession` (10/min/coach) — the two highest-frequency/cost endpoints. The other three laptop Callables are lower-frequency by nature (once per session). Broader protection (Auth sign-in abuse, general Callable flooding) is a documented Console-level gap — see Remaining Risks. |

## What this document does not claim

No scenario above was rated "mitigated" without a specific rule, function, or line cited. Where a real gap existed, it is named as a gap here and the fix is described — not silently patched without acknowledgment. Two residual, honestly-documented gaps remain (timestamp forward/backward bounds, and Console-level rate limiting/App Check enforcement) — see the Phase 13 final report's "Remaining Production Risks" section for the complete list and recommended resolution.
