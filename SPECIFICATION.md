# Vikzar Application — Master Specification

**Status:** Foundation draft. This document is the single source of truth for what the Vikzar application is and does. It will be continuously updated as each phase of the roadmap (see [ROADMAP.md](ROADMAP.md)) adds detail.

This document intentionally contains placeholders. Sections marked `_To be defined in a future phase._` are scoped but not yet specified — they should not be assumed or implemented against until filled in. Do not treat the absence of detail as permission to invent it.

Every section of this specification is subordinate to [PRODUCT_PRINCIPLES.md](PRODUCT_PRINCIPLES.md). Where a proposed spec detail would conflict with a principle, the principle takes precedence and the conflict should be resolved (and recorded in [DECISIONS.md](DECISIONS.md)) before the spec is finalized.

## 1. Overview

Vikzar is a sports technology platform focused on football injury prevention. The application described in this specification is the companion software for Vikzar wearable hardware, used by players and coaches to connect devices, monitor live sensor data, review session history, and receive AI-powered injury insights.

**Tagline:** Know Every Impact.

## 2. Goals

- Give players visibility into their own impact exposure and session history.
- Give coaches live, real-time visibility into their team's sensor data during sessions.
- Provide a reliable, low-friction connection between Vikzar hardware and the Vikzar system — via a laptop-based pipeline for MVP (see [ARCHITECTURE.md §7](ARCHITECTURE.md#7-ble-architecture)) — with results synchronized to the application in near real time.
- Surface AI-powered injury insights, generated by the injury-analysis pipeline (laptop-based for MVP), to the appropriate users via Firebase.
- Support the above across phone, tablet, and desktop form factors from a single codebase.

## 3. Non-Goals (MVP)

- Vikzar is not a general-purpose team management or communication platform.
- Vikzar does not provide medical diagnosis. Insights are informational, not clinical diagnoses.
- Roles beyond Player and Coach (e.g. clinician, club administrator) are not in scope for MVP.
- Flutter Web is not a build target for MVP; the architecture must remain compatible with adding it later.

## 4. User Roles

### 4.1 Player

_To be defined in a future phase._ Expected to cover: personal profile, own device connection, own live session view, own session history, own notifications.

### 4.2 Coach

_To be defined in a future phase._ Expected to cover: team management, live team monitoring across multiple players simultaneously, team/individual session history, team device management, notifications.

### 4.3 Role Model Notes

**Resolved (Phase 2A, data model finalized at the Phase 2 freeze review):** a single account can hold both a Player workspace and a Coach workspace, switchable in-app without logout — see [DECISIONS.md ADR-031](DECISIONS.md#adr-031-single-application-with-player-and-coach-workspace-switching) and [DESIGN_SPECIFICATION.md §13](DESIGN_SPECIFICATION.md#13-navigation-architecture). This resolves the product-level question of whether a user can hold both roles. The underlying data model — `users/{uid}.workspaces` (a structured object, one optional key per workspace held) and `users/{uid}.defaultWorkspace` (the onboarding-time fallback; the *currently active* workspace is local device state, never stored in Firestore) — is fully specified in [BACKEND_SPECIFICATION.md §1.5](BACKEND_SPECIFICATION.md#1-complete-firestore-schema). Nothing remains open on this question. How a Player is associated with a Coach's team remains defined by [BACKEND_SPECIFICATION.md §6](BACKEND_SPECIFICATION.md#6-team-ownership-model) (team membership via `teams/{teamId}/members`).

## 5. Hardware Overview

The application is the software counterpart to Vikzar's wearable hardware line. Hardware is a category the application integrates with, not a fixed pair of devices — the device model should be treated as extensible.

### 5.1 Smart Pod

Mounted on or inside football shinguards. Worn during matches and training. Primary sensing device.

- Sensor data model: _to be defined in a future phase._
- Firmware/BLE protocol details: _to be defined in a future phase._

### 5.2 EMG Thigh Band (Optional)

Wireless, thigh-worn. Used during training sessions to capture muscular activity data.

- Sensor data model: _to be defined in a future phase._
- Firmware/BLE protocol details: _to be defined in a future phase._

### 5.3 Device Extensibility

For MVP, BLE connectivity to Smart Pod and EMG Thigh Band hardware is performed entirely by a laptop-based pipeline, external to the Flutter application (confirmed architecture; see [ARCHITECTURE.md §7](ARCHITECTURE.md#7-ble-architecture) and [DECISIONS.md ADR-030](DECISIONS.md#adr-030-laptop-centric-ble-etl-and-ml-pipeline-for-mvp)). Extensibility to future hardware types is therefore primarily a laptop-pipeline concern for MVP, specified at its Firebase-facing boundary in [BACKEND_SPECIFICATION.md](BACKEND_SPECIFICATION.md). A Flutter-side device-extensibility design (a `BleService` with per-device-type protocol adapters) remains documented for the future direct-connectivity capability described in [ARCHITECTURE.md's Future Evolution section](ARCHITECTURE.md#future-evolution).

## 6. Platform Requirements

The application is a single Flutter codebase supporting:

- Android phones
- Android tablets
- iPhone
- iPad
- macOS
- Windows
- Linux

The architecture must remain compatible with adding Flutter Web support in the future, even though Web is not an MVP target.

Design and implementation must favor responsive and adaptive layouts over platform-specific implementations wherever practical. The application is not to be optimized for phones alone — coach workflows in particular should scale naturally to tablets and desktop, taking advantage of larger displays rather than simply stretching a phone layout.

The adaptive layout mechanism (breakpoint-based, single widget tree per screen rather than per-platform screens) is defined in [ARCHITECTURE.md §20](ARCHITECTURE.md#20-responsive-layout-strategy). Specific breakpoint values and per-screen adaptive behavior are defined in Roadmap Phase 2 (Design Foundations).

## 7. MVP Feature Set

The following features constitute the MVP. Each is scoped here at a high level; detailed behavior, flows, and UI will be added in future phases as the corresponding section is developed. Every feature listed here must continue to satisfy [PRODUCT_PRINCIPLES.md](PRODUCT_PRINCIPLES.md), in particular Principle 4 (clear value to players, coaches, or clinicians).

### 7.1 Authentication

Account creation and sign-in for Players and Coaches.

_To be defined in a future phase._

### 7.2 BLE Device Connection — Laptop Responsibility for MVP

**Not a Flutter application feature for MVP.** Discovering, pairing, and connecting to Vikzar hardware (Smart Pod, EMG Thigh Band) over Bluetooth Low Energy is performed entirely by a laptop-based pipeline external to the Flutter application, per the approved MVP architecture ([DECISIONS.md ADR-030](DECISIONS.md#adr-030-laptop-centric-ble-etl-and-ml-pipeline-for-mvp); [ARCHITECTURE.md §7](ARCHITECTURE.md#7-ble-architecture)). The Flutter application has no BLE pairing flow, no BLE plugin, and no direct hardware connection at MVP. Its only device-related capability is read-only status visibility (assignment, battery, connection status), covered under §7.9. Direct phone-to-wearable BLE connection is a documented future capability, not part of the MVP roadmap — see [ROADMAP.md, Out of Scope for This Roadmap](ROADMAP.md#out-of-scope-for-this-roadmap) and [ARCHITECTURE.md, Future Evolution](ARCHITECTURE.md#future-evolution).

### 7.3 Live Sensor Streaming (Display Only)

Real-time display, within the Flutter application, of already-processed sensor-derived metrics (load, impact count, risk score/level, and — where an EMG band is worn — muscle activation) for an in-progress session. The Flutter application does not stream from a connected device directly; it subscribes to live data synchronized by the laptop pipeline via Firebase. See [BACKEND_SPECIFICATION.md §8](BACKEND_SPECIFICATION.md#8-live-session-data-model) for the live session data model and [§22](BACKEND_SPECIFICATION.md#22-flutter-read-contract) for the exact read contract.

### 7.4 Live Team Monitoring

Real-time view, available to Coaches, of live sensor data across multiple players on a team simultaneously during a session. This is an MVP feature, not a post-MVP enhancement (see [PRODUCT_PRINCIPLES.md](PRODUCT_PRINCIPLES.md) Principle 3).

_To be defined in a future phase._

### 7.5 Session History

Historical record of past sessions, viewable by Players (own sessions) and Coaches (team sessions).

_To be defined in a future phase._

### 7.6 Player Profiles

Player-level profile information.

_To be defined in a future phase._

### 7.7 Team Management

Coach-facing management of a team/squad roster.

_To be defined in a future phase._

### 7.8 AI-Powered Injury Insights

Insights derived from sensor data, generated by the injury-analysis pipeline — the laptop-based ETL, feature extraction, machine learning, and Risk Engine pipeline for MVP (see [ARCHITECTURE.md §14](ARCHITECTURE.md#14-ai-analysis-pipeline) and [BACKEND_SPECIFICATION.md §12–§13](BACKEND_SPECIFICATION.md#12-alert-model)) — and surfaced to the appropriate users via Firebase synchronization. These insights are informational and not a clinical diagnosis.

### 7.9 Device Management

Flutter-side management of a user's or team's registered devices: viewing assignment, connection/battery status, and reassigning a device to a player or team. For MVP this is read-mostly with respect to device *state* (status/battery/last-seen are written by the laptop pipeline, per [BACKEND_SPECIFICATION.md §7](BACKEND_SPECIFICATION.md#7-device-ownership-model)); a coach may write assignment fields (`ownerId`, `assignedTeamId`) directly. There is no in-app pairing flow at MVP (§7.2).

### 7.10 Notifications

Notifications to Players and/or Coaches.

_To be defined in a future phase._

## 8. Architecture

Defined in Phase 1. The full engineering blueprint — application architecture, state management, navigation, dependency injection, repository pattern, BLE architecture, cloud architecture, and all supporting technical decisions — lives in [ARCHITECTURE.md](ARCHITECTURE.md), with each decision individually logged in [DECISIONS.md](DECISIONS.md) (ADR-005 onward).

In summary: a single Flutter codebase using a layered (presentation/domain/data) architecture organized feature-first, Riverpod for state management and dependency injection, go_router for adaptive role-based navigation, and Firebase (Authentication, Firestore, Storage, Cloud Functions, Cloud Messaging) as the backend platform. See [ARCHITECTURE.md](ARCHITECTURE.md) for the complete reasoning behind each choice and the open questions still pending resolution.

The backend side of this architecture — including the role of a laptop-based BLE/ETL/Machine Learning pipeline in performing all Bluetooth communication, sensor computation, and risk prediction, with Firebase strictly limited to synchronization and storage — is fully specified in [BACKEND_SPECIFICATION.md](BACKEND_SPECIFICATION.md). The discrepancy previously flagged between that document and §5.3/§7.2 below has been resolved: [DECISIONS.md ADR-030](DECISIONS.md#adr-030-laptop-centric-ble-etl-and-ml-pipeline-for-mvp) confirms the laptop-centric architecture for MVP, and this specification, [ARCHITECTURE.md](ARCHITECTURE.md), [BACKEND_SPECIFICATION.md](BACKEND_SPECIFICATION.md), and [ROADMAP.md](ROADMAP.md) now describe the same system architecture.
